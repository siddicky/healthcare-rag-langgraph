PHASE 5 — CORS check
============================================================
First attempt used SERVER_LOCAL_DEV=1 (needed for the native langgraph_smoke.py run in
Phase 2). DISCOVERED: with SERVER_LOCAL_DEV=1, server/auth.py's AuthMiddleware converts
ANY 401 into a StudioUser session (`if self.local_dev and exc.status_code == 401: return
_studio_user()`) — this is documented, intentional dev-only behavior (explicitly called
out throughout docs/deploy.md as "NEVER set in production"), NOT a security bug. It made
check (c) untestable in that posture (a garbage bearer returned 200, not 401).
REBOOTED with SERVER_LOCAL_DEV=0 (true production posture, no bypass) specifically to
test check (c) correctly. Persistence re-verified intact across this second reboot too.

(a) OPTIONS /threads, Origin header, Access-Control-Request-Method: POST, NO auth:
    HTTP/1.1 200 OK
    access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS
    access-control-allow-credentials: true
    access-control-allow-origin: http://localhost:3000
    -> PASS: preflight succeeds unauthenticated, methods widened as designed.

(b) Credentialed GET /threads/{id}, valid fresh bearer, Origin header:
    HTTP/1.1 200 OK
    access-control-allow-origin: http://localhost:3000
    -> PASS: successful response carries ACAO.

(c) SAME call with a genuinely invalid bearer ("Bearer this-is-not-a-valid-jwt-at-all"),
    under SERVER_LOCAL_DEV=0 (production posture, no bypass):
    HTTP/1.1 401 Unauthorized
    access-control-allow-origin: http://localhost:3000
    {"detail":"Unauthorized"}
    -> PASS: the exact core claim of the CORS fix. A real 401, in real production
       auth posture, still carries ACAO — the browser can read this and react
       (e.g. trigger a re-authentication flow) rather than seeing an opaque CORS
       failure.

    SEPARATE FINDING (out of scope, documented for the record): the .env-committed
    LANGGRAPH_U1_TOKEN, which is EXPIRED per its decoded `exp` claim, was accepted
    (200) rather than rejected (401) by the real supabase_bearer handler in
    healthcare_rag/agent/auth.py. This suggests JWT expiry may not be locally
    enforced by that handler (it may rely on Supabase's own session validation
    semantics, or on a different check I have not traced further). This is
    PRE-EXISTING behavior in healthcare_rag/agent/auth.py — a file NONE of this
    plan's todos touched (the CORS fix only reordered server/app.py's middleware
    list; it never modified any auth VALIDATION logic). Recorded here as an
    out-of-scope observation, not remediated, per this plan's explicit scope
    boundary (no auth-logic changes were requested or made).
